# Task 19 Excel Streaming Qualification

Status: REJECTED for production use after flow-control qualification. Task 19 implementation remains incomplete.

## ExcelJS Blocker

- Tested dependency: `exceljs@4.4.0`.
- Used the documented `ExcelJS.stream.xlsx.WorkbookReader` API with a `Readable` source.
- A valid XLSX generated by ExcelJS itself reproduces `Cannot read properties of undefined (reading 'sheets')`.
- Mutating undocumented `reader.model` internals is rejected because it does not correctly resolve shared strings and is not a supported API.
- `Workbook.xlsx.load(...)` is rejected because it requires a full workbook buffer.
- Do not patch `node_modules` or vendor a private ExcelJS modification.

## Alternative Qualification

- Candidate: `xlsx-extract@0.2.0`, repository `ffalt/xlsx-extract`.
- Source metadata requires Node.js `>=20`; this project satisfies that runtime requirement.
- API: `new XLSX().extract(filename, { sheet_nr: '1', format: 'array' })` emits `row`, `error`, and `end` events.
- Input: documented/source API accepts a filename/path, not an HTTP `Readable`.
- Source uses `yauzl` and SAX parsing and emits rows incrementally. It does not accumulate worksheet rows/cells or an XLSX file buffer, but it does retain workbook metadata and the complete shared-string table in order to resolve shared-string cells. This is bounded by workbook metadata plus unique strings, not by all worksheet rows, and remains a memory trade-off to document if adopted.
- Qualification test: an ExcelJS-generated fixture with a header, repeated strings, decimal prices, integer quantities, and multiple rows emits ordered resolved values. A corrupt archive emits an error.
- Maintenance: package metadata identifies the active upstream repository and a current `0.2.0` release; no source patch is proposed.

## Contract Impact

`xlsx-extract` requires bounded temporary-file staging:

```text
Busboy file Readable -> bounded temporary XLSX file -> XLSX row events -> row normalization/bounded batches -> delete in finally
```

The upload can remain streaming to disk with size enforcement while receiving bytes, and the parser can consume row events incrementally without retaining all rows. The temporary file is not durable storage and must be removed on both success and failure.

However, XLSX parsing cannot begin until the upload has reached EOF and the temporary file is complete. The approved SPEC/PLAN/test-contract amendment therefore replaces the HTTP-EOF assertion with proof that the first full batch can enqueue before parser/workbook EOF after staging. This parser was subsequently rejected for production use because its public EventEmitter API cannot apply asynchronous consumer backpressure; a 200-row runtime test emitted every row before the first asynchronous consumer completed. Task 19 implementation remains incomplete.
